# Common DB Log Service

Inject the existing `kr.kwater.hdcs.log.service.LogService` into other Spring
services. Reads and writes use the existing `tb_log` / `tb_event` tables.
Apply `log_audit_retention_postgresql.sql` before deploying the current version.
See [LOG_RETENTION.md](LOG_RETENTION.md) for authentication audit, heartbeat and retention policy.

```java
@Service
@RequiredArgsConstructor
public class DeviceOperationService {
    private final LogService logService;

    public void recordReceiveResult(Long deviceId) {
        long logId = logService.saveLog(deviceId, LogLevel.INFO, "DCS received");
    }

    public void recordSettingChange(String authenticatedUserId) {
        long eventId = logService.saveEvent(
                authenticatedUserId, "SETTING_CHANGED", "Device port updated");
    }
}
```

- `saveLog`: existing positive device ID, `LogLevel.DEBUG/INFO/WARN/ERROR`,
  nonblank message up to 1000 characters.
- `saveEvent`: existing user ID (up to 50 characters), nonblank event type
  (up to 30 characters), nonblank message (up to 1000 characters).
- IDs are generated by the existing DB defaults/sequences and returned as
  `long`. `REG_DT` is assigned by DB `LOCALTIMESTAMP`, using the connection's
  DB session time zone (PostgreSQL: the current transaction's start time). Configure
  the DB session time zone consistently across the application.
- Input is not silently truncated. Foreign keys validate that the device/user
  exists; do not invent device IDs or use an unregistered `SYSTEM` user.
  Obtain the actor from the authenticated security context, not untrusted
  request input. Keep credentials, tokens, raw video and large payloads out of
  messages. No automatic masking is performed.
- Writes are synchronous and transactional (`REQUIRED`). Without a caller
  transaction, each call commits on success. Within a caller transaction, logs
  commit or roll back together with the business changes. Database failures
  propagate to the caller, not a false success or a fallback print statement.
  Do not catch a persistence failure inside an active business transaction and
  assume it can still commit. Failure audit records that must survive a
  business rollback require a separate transaction boundary after rollback;
  this service does not implement an independent audit transaction.
- The existing log/event list API and report queries can read these rows.
  Existing services do not automatically emit DB records: call this service
  explicitly where a business operation succeeds or a device event occurs.
  SLF4J/Logback file output remains separate from database rows.
- Authentication flows now use the separate `AuthAuditService` and durable
  journal, which survives business rollbacks and retries DB writes after outages.
  `LogMaintenance` supplies one-second file heartbeats and file fsync.
  The DB migration, Logback policy and storage deletion guard enforce minimum
  five-year retention. General `LogService` methods retain their synchronous
  caller-transaction contract; they are not automatically spooled.

## Verification

`mvn -Dtest=LogServiceTest test` uses an isolated in-memory H2 database and the
production MyBatis mapper. It never connects to the configured PostgreSQL
server. Covers generated IDs, existing list/filter compatibility, validation,
parameter binding, FK rejection and caller transaction rollback. PostgreSQL
deployment should also validate defaults/sequences, column sizes, foreign keys
and the application account's INSERT/sequence privileges.
